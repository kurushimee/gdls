# 07. Maintenance

gdls is a port. Its correctness is defined by an upstream project that keeps moving, so maintenance is mostly about staying in sync with Godot and keeping the measurements honest.

## 1. Tracking Godot

The source of truth is a local checkout of official Godot (`godotengine/godot`), carrying every supported tag (`4.6.3-stable`, `4.7.2-stable`) with HEAD at the newest, never these documents. `git diff 4.6.3-stable 4.7.2-stable -- modules/gdscript/` is what a dialect guard owes.

When Godot ships a new feature release, re-apply the corresponding tokenizer, parser, and analyzer diffs from the Godot tree, and in the same change: refresh the vendored corpora (`06-testing-fidelity.md` §1, via `scripts/conformance/demote_corpus.py`), vendor the new stock API asset (§2), and add the `Dialect` variant. Because newest-is-primary, the unguarded body of every ported function becomes the new tag and the previous behavior is what gets wrapped — never the other way around.

This is why the port mirrors Godot's structure function for function. Structural parity is what keeps an upstream diff re-applicable; a "cleaner" Rust rewrite of a function would have to be re-derived from scratch every time that function moves.

**Derive, do not transcribe.** Every enum, count, and message template comes mechanically from the Godot source. Confirmed at both supported tags: `TokenKind` has 100 kinds in each (`gdscript_tokenizer.h`), unchanged between them. The warning set is 45 active plus 3 deprecated (`gdscript_warning.h`, the 3 behind `#ifndef DISABLE_DEPRECATED`) for 48 codes at 4.6, and 46 plus 3 for 49 at 4.7. The names and the release each first appeared in live in one table, `gd_syntax::warning_names::WARNINGS`, which `gd_analyze` projects into its own parallel arrays under compile-time asserts — Godot's parser reads the same header, and gdls needs the names in both crates. `TokenKind` is `#[repr(u8)]` indexing a parallel names table, with a `const _: () = assert!(...)` guard in `token.rs` that fails the build if the two drift apart.

**Renames are a last resort.** A symbol is renamed only when a Rust keyword forces it (`SELF` to `SelfKw`, `TK_CONST` to `Const`), and the reason is documented at the site.

## 2. Regenerating the native API

`extension_api.json` is regenerated whenever Godot's native classes change, which in practice means on every engine rebuild. In a session that happens on its own: the watcher reloads the DB when the file changes, and the auto-dump regenerates when the binary or the project's `.gdextension` set changes (`03-indexing-freshness.md` §1).

The embedded stock surfaces, the fallback for a machine with no Godot at all, are regenerated by `scripts/regen-stock-api.py`. There is one asset per supported feature release, since a 4.6 project asking a 4.7 surface about its engine classes gets wrong signatures, wrong enum values, and classes that do not exist for it yet; `embedded_stock_bytes` has one `include_bytes!` arm per `Dialect`, so adding a release fails the build until its asset is vendored. Each must be built with `--dump-extension-api-with-docs` from a stock binary of the matching release, run outside any project. The script names the output from the dump's own header, so it cannot overwrite another release's asset. `embedded_stock_db_loads` pins the prose so a regeneration with the wrong flag fails loudly instead of silently emptying every hover, and it checks each asset really is the release it is filed under.

`extension_api.json` is a strict subset of what `ClassDB` resolves, so two generated tables in `gd_types` carry the difference: `DUMP_OMITTED_NATIVE_METHODS` (the names, 182 rows) and `DUMP_OMITTED_VIRTUAL_SIGNATURES` (the real signature of the twelve rows that are genuine engine virtuals). `scripts/regen-dump-omitted-methods.sh <godot-binary>` emits both, name table first and signature table after a marker line, and the version guard refuses a binary that does not match the vendored dump. Regenerate them in the same change that bumps the stock asset. The twelve signed rows are load-bearing twice over: they are what `func <cursor>` renders as an override stub, and what the override-compatibility check measures a user's `_to_string` or `_notification` against. The other 170 stay name-only on purpose, since inventing a signature for an internal `MethodBind` would arm the arity check against a method the dump never described.

A native surface can also disagree with the dialect without being the embedded one: a pinned `extensionApiPath` left over from an upgrade, a cached auto-dump from the binary that used to be on `PATH`, a checked-in `extension_api.json`. All of them arrive stamped `Exact`, the claim that unlocks every negative diagnostic gdls emits, and an *older* dump cannot carry it — each API the newer release added is missing, and the miss reads as a user error. `reconcile_release` acts on that: it swaps in the embedded stock surface for the declared release, which is complete for it, and tells the user which dump was ignored and how to fix it. Where no embedded asset is available the older dump is kept but demoted to `Generic`, so it can no longer disprove names it never knew. A *newer* dump is left alone, since absence from a superset still proves absence from the older engine. The whole thing is skipped when nothing declared a release (`DialectOrigin::is_evidenced`): gdls guessed the newest, and the dump's own header is the better witness.

## 3. The ratchets

Both ratchets sit at 1.0000 with empty known-failures lists (`06-testing-fidelity.md` §3). CI enforces both on every change, which is what prevents silent fidelity regressions as the port evolves.

Raising a floor is deliberate: update the floor file and say so in the commit message. Lowering one is not a normal operation — the one time it happened, the corpus itself had been replaced with a larger one, and the reason is written into the floor file's header.

## 4. The release gate

Before tagging a release, run the diagnostics sweep on both acceptance projects, comparatively against the previous release binary (`06-testing-fidelity.md` §6). `--strict` plus the warning histogram, error baselines holding, and the private project swept on Windows with the Windows binary. A navigation walk is not a diagnostics gate.

The five-target fuzz gate (`parse`, `analyze`, `index_invariants`, `complete_context`, `scene_parse`) runs before a release too. Any panic blocks it.

CI runs the same four steps on `ubuntu-latest` and `windows-latest`. The local loop only covers the Linux half, and the Windows leg has stayed red across a dozen merges before because nothing in the merge loop surfaces it. Check `gh run list --branch main` after merging.

## 5. Known risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Analyzer fidelity gaps, gradual and `Variant` typing especially | High | Corpus plus differential oracle plus per-warning unit tests; ratcheted CI fidelity metric. |
| `.out` corpus mixes runtime and debug output | Medium | The curation layer filters down to the parse and analyze subset. |
| GDScript evolves across 4.x | Low to medium | Track the Godot source; re-port from the gdscript-module diffs. Behavioral differences are fenced by `Dialect` guards (§1) so older releases keep working, with the delta tables in `02-frontend-port.md` §11c and §11d as the audit surface. |
| `extension_api.json` drifts from a rebuilt engine | Medium | The watcher reloads on change; the auto-dump regenerates; degrade gracefully if stale or absent. |
| GDExtension classes absent from the API dump, or shipping no docs | Medium | Multi-source capture (in-project dump plus `doc_classes` XML); enumerate via `.gdextension`; degrade to dynamic with a notice. |
| Performance at 10k files | Medium | Eager-interface and lazy-body split; dependency-tracked invalidation; the memory-pressure ladder; the warm-start cache. |
| LSP position-encoding and large-file edge cases | Low | UTF-16 conversion tests; incremental sync tests; UTF-8 and UTF-32 negotiation. |
| Scope creep into running GDScript | Low | An explicit non-goal; the compiler and VM are excluded by design. |
